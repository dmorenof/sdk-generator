# SDK Generator 0.2.0 — Casafari functional acceptance

**Draft / work in progress**, not a new release. The goal is to automate the existing comfortable OO Casafari SDK development workflow: generate a standalone typed client with common Core behavior inherited once, not repeated per operation.

## First implemented slice

- Core/DTO: JsonSerializable, Stringable, construction from a JSON-like object, recursive nested typed objects, enum and typed collection hydration, absent vs null.
- Required fields are checked both when constructing incoming DTOs and before serializing outgoing DTOs; no HTTP call for missing required fields.
- Core/Request and Core/Response are generic DTO subclasses without Casafari-specific fields.
- Core/TypedArray wraps the existing TypedArray dependency once and exposes getExpectedType and Stringable.
- Core/HttpClient implements the common PSR-18 transport and ordered before/after HTTP middleware hooks. Core/ApiClient provides the inherited constructor and registration method, while concrete generated API classes keep their typed operations. The adapter remains Guzzle-compatible, without a second HTTP library.
- Unambiguous root input models extend Core/Request; unambiguous root output models extend Core/Response; models serving both roles or only as auxiliary models extend Core/DTO. All share Core/DTO behavior without duplicating it. Collections extend Core/TypedArray. JSON response hydration uses the same DTO construction path. Typed nested arrays accept pre-hydrated DTOs and backed enum objects without copying their identities.
- Automated acceptance checks use the unrelated synthetic Accounts API; pre-existing Catalog and all three Swagger/OpenAPI dialect fixtures remain mandatory.

## Naming policy (confirmed)

- The SDK's optional PHP root namespace comes from OpenAPI/Swagger `info.title`, e.g. `Casafari CRM API` → `CasafariCrmApi`; an explicitly passed namespace is authoritative.
- A dotted schema identifier always retains all of its hierarchical segments: `Casafari.Crm.Api.Dtos.Agency.AgencyDto` → `src/Casafari/Crm/Api/Dtos/Agency/AgencyDto.php`.
- **No inferred prefix stripping**, special treatment for one provider, or implicit rewriting of a flawed schema. PHP reserved words and filesystem collisions must be reported clearly.
- CLI may use `generate-sdk.php spec.json output vendor/package` to infer namespace from metadata or the existing `generate-sdk.php spec.json output Vendor\\Sdk vendor/package` to use an explicit namespace. The package name remains a separate Composer concern.

## Third working slice — OpenAPI validation and typed HTTP errors

- Core/DTO implements `validate()` once; generated DTOs and parameterized Requests contain typed properties and optional `protected const array VALIDATION` metadata.
- Supported declarative constraints: `minLength`, `maxLength`, `minimum`, `maximum`, `minItems`, `maxItems`. Absent optional fields are ignored; nullable nulls are valid; nested DTOs and typed DTO collections are checked recursively.
- Construction from JSON and pre-send serialization both validate, even when objects were modified after construction. Derived DTOs may override the parent validator.
- Generated PHP array literals use `[]` for required-field sets, validation maps, and operation catalogs; not legacy `array(...)`.
- Core/ApiException extends RuntimeException and contains original HttpResponse (status, raw body, headers). Explicit non-success reference schemas hydrate error DTOs. A `default` schema supplies a fallback.
- On malformed error DTOs/JSON, ApiException retains raw HTTP evidence and the original parsing failure in its exception chain; unknown errors have `error === null`.
- Transport/middleware exceptions remain their original types; middleware is optional.

**Not yet complete:** item-level constraints, pattern/format rules, polymorphic schemas, arbitrary response media, external references, query wire-name mapping and security schemes. No claim of complete contemporary Casafari compatibility.
## Not implemented yet

- Generate dedicated Response wrappers for schemas reused in input and output roles, and resolve richer media types and response shapes.

## Second working slice — named operation requests

- Operations with path, query or header arguments accept one generated, strongly typed `Requests/<Operation>Request` object; optional fields remain optional and are omitted on the wire when uninitialized.
- Operations with only a request body continue accepting their schema's generated model, which inherits `Core\\Request` when exclusively used for input.
- Operation Request DTOs validate mandatory path/query/header fields before transport. A mixed parameter-plus-body operation carries its typed `body` DTO inside the operation Request.
- The change intentionally breaks the older scalar-argument API of the 0.1.0 preview; this is a prerelease 0.2.0 API evolution.
- Extend HTTP middleware for advanced contract-driven concerns and test a real-world API, while preserving Guzzle PSR-18 customization and easy zero-config use.
- Full Casafari v1 Swagger generation and test equivalence; current spec parser supports only a small subset.
- Contract-based validation beyond required fields and native PHP types (ranges, patterns, formats, advanced schema and wire aliases).
- Prove parity with Casafari behavior without spreading vendor-specific Success/Errors fields or servers into unrelated clients.
- Benchmark CPU, memory and code volume only AFTER equivalence, not instead of it.

## Specific choices subject to further review

Unknown fields currently fail as in Casafari. JSON empty object is treated as an empty typed list as in Casafari. Both should ultimately be controlled by the actual API contract where possible.

The generated package needs no separate dmorenof/sdk-runtime package. The 0.1.0 release/tag remains immutable; this draft does not change VERSION.
